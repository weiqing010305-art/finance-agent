## 问题 1：Docker 构建卡死 20+ 分钟

### 现象

```bash
docker compose --profile core up -d --build api worker dispatcher
# 长时间无任何输出，卡在拉取基础镜像阶段
docker pull hello-world
# error: ...via direct connection because Docker Desktop has no HTTPS proxy...
#        connectex: ...failed to respond
```

### 误判过程（重要教训）

1. **第一次误判**：看到 `docker info` 里 `HTTP Proxy: http.docker.internal:3128`，判断是代理挡住了拉取，建议"关掉代理走直连"。
2. **实际结果**：直连同样超时 —— 说明**当前网络本身访问不到 Docker Hub**。关代理只是把"代理不通"换成了"直连不通"。
3. **修正结论**：必须二选一 —— 要么配一个**真正可用的代理**，要么配**国内镜像源（registry-mirrors）**。

### 又一个坑：改错了配置文件

先后尝试改 `settings.json`、`settings-store.json` 的 `dockerEngine` 字段，均无效：

- 新版 Docker Desktop 的配置文件是 `settings-store.json`（不是 `settings.json`）；
- 但**即使写对了 `settings-store.json`，`docker desktop restart` 也不会用它重新生成引擎配置**。

### 根因

WSL2 引擎在重启时**直接读取 `C:\Users\<用户>\.docker\daemon.json`**，这才是生效的那份配置。

### 解决方案 ✅

创建 / 编辑 `C:\Users\31129\.docker\daemon.json`：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://mirror.baidubce.com",
    "https://hub-mirror.c.163.com",
    "https://docker.1ms.run"
  ]
}
```

然后重启：

```powershell
docker desktop restart
# 等待约 1 分钟，托盘小鲸鱼变绿
```

### 验证

```bash
docker pull hello-world
# Status: Image is up to date for hello-world:latest   ✅
```

最终 `docker compose --profile core up -d --build` 完成 **12/12**，所有服务 Up / healthy。

### 附带注意

构建期内的 `pip install` / `npm install` 走官方源仍然会挂。若后续要重建镜像，建议在 Dockerfile 内改用国内源：

```dockerfile
RUN pip config set global.index-url https://mirrors.aliyun.com/pypi/simple/
# npm: npm config set registry https://registry.npmmirror.com
```

## 问题 2：PowerShell 修复脚本反复失败

一连串工具链层面的坑，值得单独记一笔，因为每一个都会伪装成"Docker 又坏了"。

| 报错 | 真实原因 | 解决 |
|---|---|---|
| `.\fix-docker2.ps1 : 无法将...识别为 cmdlet` | 在错误的目录下执行，脚本不在当前路径 | `cd` 到脚本所在目录，或用绝对路径 |
| `ParserError` + 中文变成 `[瀹屾垚]` | 脚本文件以 GBK 写入，PowerShell 按 UTF-8 解析 | 脚本内**只写英文**，避免非 ASCII 字符 |
| Docker 守护进程改完配置后**彻底起不来** | `Set-Content -Encoding UTF8` 会写入 **BOM**，Docker 的 Go JSON 解析器无法处理，配置文件损坏 → daemon 拒绝启动 | 见下方写法 |

### UTF-8 无 BOM 的正确写法

```powershell
$p = "C:\Users\31129\.docker\daemon.json"
$s = '{ "registry-mirrors": ["https://docker.m.daocloud.io"] }'
[System.IO.File]::WriteAllText($p, $s, [System.Text.UTF8Encoding]::new($false))
```

> **通用教训**：PowerShell 5.1 下，凡是要写给 Go / Rust / Node 程序读的 JSON、YAML 配置，都不要用 `Set-Content -Encoding UTF8`，必须用 `UTF8Encoding($false)`。

## 问题 3：`npipe dockerDesktopLinuxEngine` 找不到

### 现象

```
error during connect: ... open //./pipe/dockerDesktopLinuxEngine:
The system cannot find the file specified.
```

### 根因

这个命名管道**只在 Docker Desktop 运行时存在**。这台机器上 Docker Desktop **不会开机自启**，所以每次重启电脑后必然复现。

### 解决方案 ✅

```powershell
& "C:\Program Files\Docker\Docker\Docker Desktop.exe"
# 等约 1 分钟，托盘图标变绿后再执行 docker 命令
```

> 注意区分：此报错 ≠ 配置问题，也 ≠ 网络问题。看到它先确认 Docker Desktop 是否在跑。

## 问题 4：`bootstrap` 提示"已完成"但无法登录

### 现象

执行 `scripts\local.ps1 bootstrap` 返回"已完成 / already complete"，但拿不到任何可用凭据。

### 根因

数据库里的 owner 账号在之前的某次运行中**已经创建过**，bootstrap 是幂等的，检测到已存在就直接跳过，不再打印凭据。

### 解决方案 ✅

直连 Postgres（用 `finscope_admin` 角色，密码在 `secrets/postgres_admin_password`）查出 TenantId，再用后端自带的 argon2 哈希函数（`backend/auth/passwords.py` 的 `hash_password()`）重置密码。

**恢复出的可用凭据**：

```
访问地址 : https://localhost:8443/     （自签名证书，浏览器需手动信任）
邮箱     : owner@example.com
密码     : Finscope@2026
Tenant ID: 0888fc6d-0d4b-4fed-9a58-1f8d2d8cd04b
收件箱   : http://127.0.0.1:8025/      （Mailpit，用于收验证码/邮件）
```

> ⚠️ 前端登录框有 `minlength="12"` 校验，密码必须 ≥ 12 位。
> ⚠️ 切换到 `backend.app` 后（见问题 6），这套 formal 控制台凭据暂时用不上。

## 问题 5：前端"长得很怪"—— 其实不是 bug

### 结论

`formal-console.html` 的米黄纸质底色（`#eee9dc`）+ 橙色主色（`#ef5b2a`）+ 杂志排版，是**刻意设计的编辑风静态原型**，不是样式加载失败。

技术特征：

- 纯静态 HTML + CSS + 原生 JS，**没有 React / Vue，也没有构建步骤**；
- `formal-console.js` 直接 `fetch('/api/auth/login')`，创建研究任务后每 1.5s 轮询一次；
- `index.html` 只是个 357 字节的跳转壳（`meta refresh`）。

所以"怪"是审美取向问题，不是故障。

## 问题 6：切换前端后 `/api/securities` 一直 404 ⭐

这是本次最有价值的发现。

### 现象

按需求把服务的前端切到 `prototype-research-ui/unified-agents.html` 后：

- `GET /api/health` → **200 OK** ✅
- `GET /api/securities` → **404** ❌
- `POST /api/research`、SSE 事件流 → **404** ❌

明明源码里有 `@app.get("/api/securities")`，容器里 `grep` 也能搜到这行代码。

### 排查路径（一步步排除）

1. 怀疑 Caddy 反代规则错 → 直接在容器内 `curl 127.0.0.1:8000` 同样 404，**排除 Caddy**。
2. 怀疑镜像里代码是旧的 → `docker compose exec api grep securities backend/app.py` **能搜到**，代码是新的。
3. 怀疑路由被条件注册 → `import backend.app; print(app.routes)` 打印出的路由表里 **`/api/securities` 确实存在**。
4. 矛盾点：路由表里有，HTTP 却 404 → 说明 **uvicorn 跑的不是这个 app 实例**。
5. 决定性一步 —— 看容器实际启动命令：

```bash
docker compose exec api sh -c "cat /proc/1/cmdline | tr '\0' ' '"
# → uvicorn backend.formal_app:create_formal_app --factory ...
```

### 根因

项目里存在**两个完全不同的 FastAPI 应用入口**，而 Docker 默认跑的是前者：

| | `backend.formal_app`（Docker 默认） | `backend.app`（unified-agents.html 需要） |
|---|---|---|
| 定位 | 正式版："formal" 控制台 | 研究原型："unified" 案卷控制台 |
| 数据库 | **Postgres** | **SQLite**（`Repository`） |
| 鉴权 | 有（登录 / Tenant 隔离） | 无（硬编码 `tenant_id="local"`, `user_id="default"`） |
| 研究路由 | **刻意不暴露** | `/api/securities`、`/api/research`、SSE、pause/resume/cancel/feedback |
| 对应前端 | `formal-console.html` | `unified-agents.html` |

`/api/health` 两个 app 都有，所以健康检查通过掩盖了真正的问题 —— **这是最容易上当的地方**。

### 解决方案 ✅（共 4 处改动）

**① `compose.yaml`（第 85 行）** —— 切换 api 服务的启动模块：

```yaml
# 改前
command: [python, scripts/container_entrypoint.py, uvicorn, backend.formal_app:create_formal_app, --factory, ...]
# 改后
command: [python, scripts/container_entrypoint.py, uvicorn, backend.app:create_app, --factory, ...]
```

**② `Dockerfile`（第 19 行）** —— 同步镜像默认 CMD，避免不带 compose 启动时行为不一致：

```dockerfile
CMD ["uvicorn", "backend.app:create_app", "--factory", "--host", "0.0.0.0", "--port", "8000"]
```

**③ `prototype-research-ui/index.html`** —— 根路径重定向改指新页面：

```html
<meta http-equiv="refresh" content="0; url=./unified-agents.html">
```

**④ `prototype-research-ui/unified-agents.html`（第 354 行）** —— API 地址改为同源相对路径：

```js
// 改前：指向本地开发服务器，容器环境下必然不通，且会触发 CSP / CORS
const API_BASE = 'http://127.0.0.1:8780/api';
// 改后：走 Caddy 反代，同源
const API_BASE = '/api';
```

**⑤ `infra/caddy/Caddyfile`（第 14 行）** —— 放宽 CSP。该页面是**内联** `<style>` / `<script>`，且从 CDN 引 ECharts，原来的 `script-src 'self'` 会直接把它拦死：

```
style-src  'self' 'unsafe-inline';
script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net;
```

### 生效方式（无需重建镜像）

```bash
cd "D:\dsh-test\finance agent"
docker compose up -d --force-recreate api   # 复用现有镜像，仅换启动命令
docker compose restart caddy                # 重载 CSP
```

> HTML 文件是 bind-mount 挂进 Caddy 的 `/srv`，改完**即时生效**，连 restart 都不需要。

### 验证结果（全部实测通过）

```bash
GET  /api/health      → {"status":"ok","mode":"mock"}
GET  /api/securities  → 25 条证券别名（输入框自动识别公司名用）
POST /api/research    → 202，任务真实进入 status: running
POST /api/research/{id}/cancel → 200（测试数据已清理）
```

## 总结：三条可复用的教训

1. **健康检查通过 ≠ 服务正确**
   `/api/health` 在两个 app 里都存在，正是它让"跑错入口"这个问题隐藏了很久。排查 404 时，**先确认进程到底在跑哪个模块**（`cat /proc/1/cmdline`），比逐行读源码快得多。

2. **配置改了不生效，先怀疑改错了文件**
   Docker Desktop 有 `settings.json` / `settings-store.json` / `~/.docker/daemon.json` 三处，真正被 WSL2 引擎读取的是最后一个。

3. **Windows 上写配置文件要防编码**
   BOM 和 GBK 是两个隐形杀手：BOM 让 Go 解析器崩，GBK 让 PowerShell 解析器崩。统一用 `UTF8Encoding($false)`，脚本内容只写 ASCII。
